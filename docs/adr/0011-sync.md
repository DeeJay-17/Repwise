# 0011. Sync: whole rows, newest edit wins, server-ordered changes

- Status: accepted
- Date: 2026-11-16

## Context

Signed-in users want their data on several phones (ADR 0005 keeps the phone's SQLite as the source of truth). Guests who sign in later must bring their data with them. One person rarely edits the same row on two phones at the same moment.

## Decision

- **Server store:** `core-api` keeps every synced row as JSON in one `sync_records` table keyed by (user, table, row id), with the row's `updatedAt`, `deletedAt` and a per-user sequence number. The phone owns the schema; the server does not interpret row contents.
- **One call:** `POST /v1/sync` takes the phone's cursor and its changed rows, and returns rows changed elsewhere since the cursor (paged), plus a new cursor. It runs in one transaction with the user's counter row locked, so two phones syncing at once are serialised.
- **Conflicts:** per row, the newest `updatedAt` wins, on the server and on the phone. Deletes are soft (`deletedAt`), so they sync like edits.
- **Phone side:** push rows with `updatedAt` after the last successful push; apply pulled pages together in one transaction, parents before children. Sync runs after sign-in, when the app returns to the foreground, and five seconds after any change.
- **Accounts:** Google ID tokens from native sign-in are verified by `core-api`, which issues a one-hour JWT access token and a 60-day refresh token. Refresh tokens are single use; reusing one revokes all of that user's sessions. Signing out keeps data on the phone and resets sync progress, so the next account to sign in receives it.

## Consequences

Simple to reason about and test (the app's tests run the same rules against an in-memory fake server). Concurrent edits to the same row keep only the later one, which is acceptable for this data. Device clocks decide "newest"; a phone with a badly wrong clock can win or lose conflicts it should not. Account deletion is supported (`DELETE /v1/me`), as app stores require.
